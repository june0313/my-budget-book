# 요구사항

가계부 앱에서 무엇을 만들지, 무엇을 만들었는지, 왜 그렇게 정했는지를 기록한다.
기능을 추가하거나 결정을 바꿀 때마다 이 문서를 함께 고친다.

상태: ✅ 완료 · 🚧 진행 중 · ⬜ 할 일 · ❓ 검토 필요(만들지 말지 미정)

## 1. 목표와 범위

- 개인이 수입과 지출을 기록하고, 월 단위로 돈의 흐름을 파악한다.
- Kotlin + Spring Boot 백엔드 학습을 겸한다. 기능을 한 번에 크게 만들기보다 작게 나눠서 하나씩 완성한다.
- 백엔드 API를 먼저 만들고, 프런트엔드는 나중에 별도 디렉터리로 추가한다.

## 2. 용어

| 용어 | 코드 | 설명 |
|---|---|---|
| 거래 내역 | `Entry` | 수입 또는 지출 한 건. 날짜, 구분, 금액, 카테고리, 메모로 이루어진다 |
| 구분 | `EntryType` | `INCOME`(수입) / `EXPENSE`(지출) |
| 카테고리 | `category` | 식비, 교통, 급여 같은 분류 |

## 3. 기능 요구사항

### 3.1 거래 내역 기록

| ID | 요구사항 | 상태 |
|---|---|---|
| E-1 | 거래 내역을 등록한다 (날짜, 구분, 금액, 카테고리, 메모) | ✅ |
| E-2 | 거래 내역 목록을 최신 날짜순으로 조회한다 (월 단위, S-1) | ✅ |
| E-3 | 거래 내역 한 건을 조회한다 | ✅ |
| E-4 | 거래 내역을 수정한다 (전체 교체) | ✅ |
| E-5 | 거래 내역을 삭제한다 | ✅ |
| E-6 | 잘못된 입력은 어느 필드가 왜 틀렸는지 알려준다 | ✅ |

### 3.2 조회와 통계

| ID | 요구사항 | 상태 |
|---|---|---|
| S-1 | 특정 월의 거래 내역을 조회한다 (`?month=2026-11`, 없으면 이번 달) | ✅ |
| S-2 | 특정 월의 수입 합계, 지출 합계, 잔액(수입 − 지출)을 조회한다 | ⬜ |
| S-3 | 특정 월의 카테고리별 지출 합계를 조회한다 | ❓ |
| S-4 | 구분(수입/지출), 카테고리로 목록을 거른다 | ❓ |
| S-5 | 메모로 검색한다 | ❓ |

### 3.3 카테고리

| ID | 요구사항 | 상태 |
|---|---|---|
| C-1 | 거래 내역의 카테고리는 정해진 목록에서 고른다 (자유 입력 불가) | ✅ |
| C-2 | 기본 카테고리 목록을 제공한다 (식비, 교통, 급여 등) | ✅ |
| C-3 | 사용자가 카테고리를 직접 추가한다 | ✅ |
| C-4 | 카테고리 목록을 조회한다. 수입/지출 구분으로 거를 수 있다 | ✅ |
| C-5 | 카테고리 이름을 바꾼다 | ✅ |
| C-6 | 카테고리를 삭제한다. 단, 거래 내역이 사용 중인 카테고리는 삭제할 수 없다 | ✅ |
| C-7 | 카테고리는 수입용과 지출용으로 나뉜다. 거래 내역의 구분과 카테고리의 구분이 다르면 등록·수정할 수 없다 | ✅ |

카테고리 규칙:

- 카테고리는 이름과 구분(수입/지출)을 가진다. 같은 구분 안에서 이름은 중복될 수 없다.
- 카테고리의 구분은 만든 뒤 바꿀 수 없다. 바꿀 수 있으면 이미 그 카테고리를 쓰는 거래 내역과 구분이 어긋난다.
- 이름을 바꾸면 그 카테고리를 쓰는 기존 거래 내역에도 바뀐 이름이 보인다. (거래 내역은 이름이 아니라 카테고리를 참조한다)
- 이름은 1~20자이고, 앞뒤 공백은 지운다.
- 기본 카테고리: 지출 — 식비, 카페, 교통, 주거, 통신, 쇼핑, 문화, 의료, 기타 / 수입 — 급여, 부수입, 용돈, 기타

### 3.4 그 밖의 후보

| ID | 요구사항 | 상태 |
|---|---|---|
| B-1 | 월 예산을 정하고 남은 금액을 본다 | ❓ |
| R-1 | 월세처럼 매달 반복되는 거래를 자동으로 등록한다 | ❓ |
| P-1 | 결제 수단(현금, 카드, 계좌)을 기록한다 | ❓ |

## 4. 비기능 요구사항

| ID | 요구사항 | 상태 |
|---|---|---|
| N-1 | 금액은 원 단위 정수로 다룬다 (소수점 없음) | ✅ |
| N-2 | 에러 응답은 RFC 9457 ProblemDetail 형식을 따른다 | ✅ |
| N-3 | 로컬 실행 시 샘플 데이터가 자동으로 들어간다 | ✅ |
| N-4 | 앱을 재시작해도 데이터가 남는다 (현재는 H2 인메모리라 사라짐) | ❓ |
| N-5 | 로그인해서 내 데이터만 본다 (여러 사용자) — 지금은 하지 않고, 나중에 확장한다 | ⬜ |

### 로그인 확장을 대비한 원칙

- 거래 내역 조회·수정·삭제는 항상 Service를 거친다. 나중에 "내 데이터만" 조건을 Service 한 곳에 추가하면 되도록.
- 지금은 거래 내역에 사용자 컬럼(`userId` 등)을 미리 만들지 않는다. 쓰이지 않는 컬럼은 오히려 헷갈리고, 지금은 인메모리 DB라 나중에 추가해도 비용이 거의 없다.
- 단, 데이터가 남는 DB(N-4)로 바꾼 뒤에는 컬럼 추가에 마이그레이션이 필요하다. 그래서 N-4와 N-5 중 N-4를 먼저 하게 되면, 그때 마이그레이션 도구(Flyway 등) 도입을 같이 검토한다.
- 통계 API(S-1, S-2 등)는 "어떤 거래 내역들을 대상으로 하는가"를 Repository 조회 조건으로 표현한다. 나중에 사용자 조건을 하나 더 붙이기 쉽도록.
- 카테고리는 지금부터 "기본 카테고리"와 "사용자가 추가한 카테고리"를 구분해 둔다. 나중에 사용자가 추가한 카테고리에만 소유자를 붙이면 되도록.

## 6. 열린 질문

- 데이터를 언제부터 남겨야 하는가? 실제로 쓰기 시작하는 시점에 영속 DB가 필요하다. (N-4)
- 기본 카테고리도 이름 변경·삭제를 허용할 것인가? 지금은 허용한다. 로그인 확장 후 기본 카테고리를 모든 사용자가 공유하면, 한 사용자의 변경이 모두에게 보이므로 막아야 할 수 있다.
